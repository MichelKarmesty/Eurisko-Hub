# ADR 003: Admin Assignment and Cancellation

> **Amended by [ADR-010](ADR-010.md).** Cancellation stays soft and audited, as
> below. The absolute rule "a ticket is never hard-deleted" is **narrowed** by
> ADR-010: an Admin may permanently delete a ticket that is **Resolved**
> (`DELETE /tickets/:id`); anything else — `Open`, `In Progress`, `Cancelled` — is
> still refused and a `Cancelled` ticket remains the audited outcome.

## Problem Statement

[ADR-001](ADR-001.md) puts every ticket in a shared department queue and lets
agents claim what they can. Two operational gaps remained:

1. **Urgent work can sit unclaimed.** If no agent picks up a high-priority
   ticket, nobody owns it. An Admin could already force the status
   ([ADR-002](ADR-002.md)), but that *skips* the queue rather than fixing it —
   the ticket ends up with no assignee.
2. **Some requests should not be worked at all** — duplicates, obsolete
   requests, or something withdrawn by the requester. There was no way to retire
   one, and "erase the ticket" would destroy the history the product treats as a
   source of truth.

## Decision Options

### Assignment

* **Option A — Admin can assign an unclaimed ticket to an agent** (selected).
  The ticket gets a real owner and the normal `Open -> In Progress` transition;
  the assignee is an agent whose department matches the ticket's category.
* **Option B — keep override-only.** Simpler, but leaves ownerless tickets and
  makes the queue look pointless when an Admin steps in.

### Removal

* **Option A — hard delete.** Permanently removes the row. Rejected: it destroys
  the audit trail, breaks `ticket_events` history, and cannot be reviewed later.
* **Option B — soft cancel** (selected). The ticket keeps its row and full
  history and moves to the terminal status `Cancelled`, with a required reason.

## Selected Decision

**Admins may assign unclaimed tickets, and may cancel requests softly — never
delete them.**

* `PATCH /tickets/:id/assign` (Admin only) assigns an `Open`, unclaimed ticket
  to an agent of the matching department; it becomes `In Progress` and an
  `ASSIGNED` event records the Admin and the assignee. An agent from another
  department, a non-agent, or an already-claimed ticket is rejected.
* `PATCH /tickets/:id/cancel` (Admin only) moves an `Open`/`In Progress` ticket
  to `Cancelled` with a **required** reason; a `CANCELLED` event is recorded. A
  `Resolved` or already `Cancelled` ticket cannot be cancelled.

## Consequences & Rationale

**Benefits**
* Urgent work gets a named owner without bypassing the queue.
* Junk requests can be retired while the audit trail survives (`Cancelled`
  tickets remain readable with their full history).
* The Admin toolset is now coherent: **assign** (normal), **override with a
  reason** (exceptional, ADR-002), **cancel** (retire), **never delete**.
* `resolvedById` was added so a ticket names its *real* resolver (assigned agent
  or Admin override) instead of guessing from the assignment.

**Trade-offs**
* The lifecycle gains a fourth, terminal status. `Cancelled` is deliberately
  **not** part of the linear `STATUS_ORDER`, so `statusCanTransition` never
  allows it as a normal step — only the cancel endpoint sets it.
* Assignment is Open-only; reassigning work in progress is out of scope for now.

## Alignment with Product Requirements

* [data-model.md](../data-model.md) §2 defines `Open -> In Progress -> Resolved`;
  ADR-003 adds `Cancelled` as an Admin-only terminal state and keeps the linear
  rule intact.
* [architecture.md](../architecture.md) §3 requires enforcement at the API
  boundary: both rules live in `TicketsService` and the `@Roles('Admin')` guard,
  not the client.
* [product-spec.md](../product-spec.md) §8 Scenario 3 deferred Admin actions
  beyond viewing; ADR-002 and ADR-003 are that addition, now explicit and
  audited.

## Implementation Impact

* `backend/src/common/domain.ts` — `STATUSES` gains `Cancelled`; `STATUS_ORDER`
  is unchanged.
* `backend/src/tickets/ticket.entity.ts` — `resolvedById` / `resolvedBy`.
* `backend/src/tickets/dto.ts` — `AssignTicketDto`, `CancelTicketDto`.
* `backend/src/tickets/tickets.service.ts` — `assign()`, `cancel()`;
  `changeStatus()` sets `resolvedById`.
* `backend/src/tickets/tickets.controller.ts` — `@Roles('Admin')` routes for
  `PATCH /tickets/:id/assign` and `PATCH /tickets/:id/cancel`.
* `frontend/` — Admin "Assign" and "Cancel request" controls; the row names the
  real resolver.
* Tests — integration and HTTP suites, `scripts/verify-slice.mjs`, and the UI
  E2E (`e2e/dom/admin-actions.ui.test.tsx`).
