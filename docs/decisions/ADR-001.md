# ADR 001: Ticket Assignment Strategy

**Related Documents:** [Product Specification](../product-spec.md) | [Architecture Design](../architecture.md) | [Data Model](../data-model.md)

---

## Problem Statement

The system needs a method to determine which specific support agent handles a newly created ticket within a department (e.g., IT).
## Decision Options

The team evaluated two primary strategies for assigning tickets to agents within each department:
### Option 1: Automated Assignment (Not Selected)
Backend automatically assigns the ticket to an agent based on workload balancing algorithms. This would require complex stateful logic and real-time agent availability tracking.

### Option 2: Manual Queue Claiming (Selected) ✓
Pull-based model where tickets go to a shared department bucket (queue). Agents actively monitor their category queue and manually claim tickets they want to work on.

## Selected Decision

**Manual Queue Claiming**

## Consequences & Rationale

**Benefits:**
- Simplifies backend architecture by removing stateful assignment algorithms
- No need for complex workload-balancing logic
- Eliminates requirement to track agent real-time availability
- Agents have control over what tickets they work on (ownership and autonomy)
- Faster to implement for MVP timeline
- Easier to audit: clear record of who claimed which ticket and when

**Trade-offs:**
- Relies on human agents to actively monitor their queue
- Risk of high-priority tickets being overlooked if agents don't check frequently
- No automated load balancing (agents could theoretically claim all tickets)

**Mitigation Strategies:**
- Implement visual urgency indicators (color-coded by priority)
- Display queue refresh timestamp to encourage frequent checks
- Future enhancement: Dashboard notifications or alerts for high-priority tickets
- Supervisor oversight via admin dashboard (see all unclaimed tickets)

## Alignment with Product Requirements

This decision directly supports the product specification's constraint stated in [product-spec.md](../product-spec.md#6-assumptions-constraints--unknowns):

> "The system does not auto-assign tickets to specific agents. Agents look at the 'Open' list and manually claim what they want to work on."

## Implementation Impact

From an [architecture](../architecture.md) perspective, the Backend API Ticket Module:
- Creates tickets in the OPEN status
- Assigns them to a category-based queue (via the `category` field)
- Provides filtering endpoint: `GET /tickets?category=IT&status=OPEN` for agents
- Agent claims via endpoint: `PATCH /tickets/:id/claim` (sets `assigned_to` field)

From a [data model](../data-model.md) perspective:
- Tickets table has `assigned_to_id` field (nullable until agent claims)
- Status remains OPEN until agent explicitly claims
- No automated assignment logic needed in the database
