# ADR 001: Ticket Assignment Strategy

**Related Documents:** [Product Specification](../product-spec.md) | [Architecture Design](../architecture.md) | [Data Model](../data-model.md)

---

## Problem Statement

When a new ticket arrives, the system needs a way to decide which support agent will handle it.
## Decision Options

We considered two ways to assign tickets within each department:
### Option 1: Automated Assignment (Not Selected)
The backend assigns each ticket using workload-balancing rules. This would require stateful logic and real-time tracking of agent availability.

### Option 2: Manual Queue Claiming (Selected) ✓
Tickets go into a shared department queue. Agents monitor their queue and claim the tickets they are ready to work on.

## Selected Decision

**Manual Queue Claiming**

## Consequences & Rationale

**Benefits:**
- Keeps the backend simple by removing assignment algorithms.
- Avoids tracking each agent's real-time availability.
- Lets agents choose what they can take on.
- Is faster to build for the MVP.
- Leaves a clear record of who claimed each ticket and when.

**Trade-offs:**
- Agents need to check their queue regularly.
- A high-priority ticket could be missed if nobody checks the queue.
- Without automatic load balancing, one agent could claim too many tickets.

**Mitigation Strategies:**
- Show priority clearly with visual urgency indicators.
- Display when the queue was last refreshed.
- Add dashboard notifications for high-priority tickets later.
- Give supervisors visibility of unclaimed tickets through the admin dashboard.

## Alignment with Product Requirements

This decision directly supports the product specification's constraint stated in [product-spec.md](../product-spec.md#6-assumptions-constraints--unknowns):

> "The system does not auto-assign tickets to specific agents. Agents look at the 'Open' list and manually claim what they want to work on."

## Implementation Impact

From an [architecture](../architecture.md) perspective, the Backend API Ticket Module:
- Creates tickets in the OPEN status
- Assigns them to a category-based queue (via the `category` field)
- Provides filtering endpoint: `GET /tickets?category=IT&status=OPEN` for agents
- Agent claims via endpoint: `PATCH /tickets/:id/claim` (sets `assigned_to` field)

From a [data model](../data-model.md) perspective:
- Tickets table has `assigned_to_id` field (nullable until agent claims)
- Status remains OPEN until agent explicitly claims
- No automated assignment logic needed in the database
