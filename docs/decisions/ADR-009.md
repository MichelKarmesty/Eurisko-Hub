# ADR 009: Recovery Is Admin-Initiated — the Public Self-Service Reset Is Off by Default

**Related Documents:** [Product Specification](../product-spec.md) | [Architecture Design](../architecture.md) | [Data Model](../data-model.md) | [Security Notes](../security.md) | [API Reference](../api.md) | [ADR-004](ADR-004.md) | [ADR-007](ADR-007.md) | [ADR-008](ADR-008.md)

---

## Problem Statement

ADR-008 restored the public, self-service recovery path: `POST /auth/forgot-password`
prompts for an address and emails a one-time link, with a transport chain
(primary SMTP → backup SMTP → webhook → Resend → console), a non-enumerating
generic answer and an anti-mail-bomb cooldown.

Using the hub, that turned out to be capability nobody asked for. Eurisko Hub is
an **internal tool**: the Admin creates every account (ADR-004), knows who works
there, and is the natural owner of "I forgot my password". ADR-007 already gives
them a one-time link they can hand over for **any** account — including another
Admin — with **no mail provider at all**, and `scripts/reset-password.mjs`
covers the lone locked-out Admin offline.

Meanwhile the public path carries real cost and risk: a mail credential to
provision and keep working, deliverability and spam questions, an unauthenticated
endpoint that sends mail to arbitrary addresses, plus enumeration and
mail-bombing considerations — all in exchange for a flow the Admin does in two
clicks.

## Decision Options

### Option 1: Keep ADR-008 as it is (self-service primary) — not selected
Works, but leaves the hub with an outward-facing recovery endpoint and a mail
dependency for a job the Admin already does better (they can verify the person
asking).

### Option 2: Delete the self-service path and the mail subsystem — not selected
The leanest surface, and closest to the product's "no external service" posture.
Rejected because the transports are written, tested and documented (ADR-008), and
deleting them destroys a working capability that a different deployment may
legitimately want — for no runtime benefit, since unused code costs nothing while
it is off.

### Option 3: Keep the capability, ship it **off** — selected ✓
`POST /auth/forgot-password` answers `404` (exactly as if it did not exist)
unless the operator sets `PASSWORD_RESET_SELF_SERVICE=true`. The sign-in screen
offers **no** "Forgot password?" link: recovery is the Admin-issued link
(ADR-007) handed over in person, or the offline break-glass.

## Selected Decision

**Admin-initiated recovery is the product's recovery model, and the public
self-service path is disabled by default.**

* `POST /auth/forgot-password` → `404 Cannot POST /auth/forgot-password` while
  `PASSWORD_RESET_SELF_SERVICE` is unset or `false` (the default, and the value in
  `backend/.env.example`).
* The Admin issues the link from **Users → Reset password**
  (`POST /users/:id/reset-password`) and hands it over; the employee sets their own
  password through `POST /auth/reset-password`. The Admin never sees or chooses it.
* The offline `scripts/reset-password.mjs` break-glass stays for a lone Admin who
  has locked themselves out.
* Setting `PASSWORD_RESET_SELF_SERVICE=true` re-enables the emailed path without
  touching code; the mail transports and the setup/verify scripts are kept for
  that case (and are still covered by tests).

## Consequences & Rationale

**Benefits**
* The product's outward surface matches the product: one authenticated reset
  action, no unauthenticated mail-sending endpoint, no credential to provision.
* Nothing to configure for recovery to work — a fresh clone can reset any
  password (ADR-007), which is what the hub's users actually need.
* No work is thrown away: the ADR-008 transports remain available behind one
  environment variable, with tests and documentation intact.

**Trade-offs**
* A person who forgets their password must reach an Admin; with a single Admin
  who is also locked out, only the offline script helps (already true under
  ADR-007).
* Two states for one endpoint must stay documented and tested — the suite pins
  both `404` (default) and the full emailed flow (when switched on).
* The `404` is a deliberate imitation of "route does not exist"; a client cannot
  distinguish a disabled feature from a removed one. That is intended.

**Mitigation**
* The default is asserted by a test (`auth-password.spec.ts`), so a future change
  cannot silently expose the endpoint again.
* Enabling it is one variable, documented in `backend/.env.example`, `api.md`,
  `security.md` and `backend/README.md`.

## Implementation Impact

* `backend/src/auth/auth.controller.ts` — `forgotPassword` answers `404` unless
  `AuthService.selfServiceResetEnabled`; the class comment now lists the public
  routes as login + reset only.
* `backend/src/auth/auth.service.ts` — `selfServiceResetEnabled` (env read per
  request, default `false`).
* `backend/.env.example` and `backend/.env` — `PASSWORD_RESET_SELF_SERVICE=false`
  next to the (now optional) mail transport block.
* `frontend/src/components/AuthScreen.tsx` — the **Forgot password?** mode and
  button removed; sign-in offers **I have a reset token** and links land in the
  reset form. `api.ts` keeps `apiForgotPassword`, documented as off-by-default.
* Tests — `backend/test/auth-password.spec.ts` pins the `404` default and still
  covers the enabled flow end to end; the ADR-007 suites are unchanged.
* Docs — this ADR, an amendment banner on [ADR-008](ADR-008.md), [api.md](../api.md),
  [security.md](../security.md), [product-spec.md](../product-spec.md),
  [architecture.md](../architecture.md), the root/backend/frontend READMEs and the
  documentation index.
