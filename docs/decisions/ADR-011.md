# ADR 011: An Admin Can Set a Password Directly, Not Only Hand Over a Link

**Related Documents:** [Product Specification](../product-spec.md) | [Security Notes](../security.md) | [API Reference](../api.md) | [ADR-004](ADR-004.md) | [ADR-007](ADR-007.md) | [ADR-009](ADR-009.md)

---

## Problem Statement

ADR-007 deliberately made recovery **hand-over only**: the Admin mints a one-time
link (`POST /users/:id/reset-password`) and gives it to the person, who chooses
their own password. The Admin never sees or chooses a credential - a genuinely
good property, and the reason the link exists.

In practice that left the Admin unable to *actually reset* anything. Clicking
**Reset password** produced a link and nothing else, which is useless exactly when
the Admin needs it most: the person is sitting next to them, the account is a demo
or test account whose owner is not reachable, or the link cannot be delivered at
all (no mail provider - ADR-009). The request: **let the Admin set the password**.

## Decision Options

### Option 1: Keep hand-over only - not selected
Preserves the "Admin never knows the credential" property, but leaves the Admin
with a link they cannot use themselves and no way to unblock a person who is
present.

### Option 2: Replace the link with a direct set - not selected
Simplest surface, but it throws away the better workflow (the person picks their
own password, the Admin never learns it) which still matters for remote users.

### Option 3: Offer both - selected ✓
`PATCH /users/:id/password` (Admin only, body `{ password }`) sets a bcrypt-hashed
password immediately, **and clears any pending reset link** so an old link can
never outlive the change. The one-time link from ADR-007 remains available, and
the UI shows both in the same panel: copy the link **or** set the password now.

## Selected Decision

**An Admin may set any active account's password directly; the hand-over link
stays.**

* `200` → `{ id, email }` - the hash is never returned; the password is hashed
  with bcrypt (cost 10) like every other password.
* Any outstanding `passwordResetTokenHash` / `passwordResetExpiresAt` is cleared,
  so a previously issued link dies with the change.
* `400` - a password shorter than 8 characters; a **deactivated** account (it
  cannot sign in, so a password would be misleading - the same rule as issuing a
  link, ADR-007).
* `404` - unknown account; non-Admin caller → `403`; no token → `401`.
* The action is **logged** (`AdminPassword`: which Admin set a password for which
  account), because it is the one action where an Admin handles a credential.

## Consequences & Rationale

**Benefits**
* The Admin can genuinely restore access - including for someone standing next to
  them, or for an account whose owner is unreachable.
* Nothing else changes: the link workflow, its single-use/expiry rules and the
  employee's own **Change password** all still work.

**Trade-offs**
* **The Admin now knows a credential**, which is precisely what ADR-007 avoided.
  A leaked Admin session can therefore take over an account *without* the target
  ever seeing a link.
* Nothing forces the person to change it afterwards: the project has no
  `mustChangePassword` column, so this relies on the Admin telling them.

**Mitigation**
* Hashed at rest, never echoed; `@Exclude()`d from every response.
* Every use is logged with actor and target.
* Setting it invalidates pending links, so the two paths cannot both stay live.
* The UI says it plainly ("the Admin who sets a password knows it - tell them to
  change it from the top bar"), and `POST /auth/change-password` still requires the
  current password, so the person can rotate it at any time.
* A deactivated account is refused, so this cannot be used to revive an account
  silently while its login is revoked.

## Alignment with Product Requirements

* [security.md](../security.md) §"Password reset and change" - the credential
  rules, now with this documented exception to "the Admin never sees it".
* [api.md](../api.md) §"POST /users/:id/reset-password" - the neighbouring
  endpoint and its contract; the new one is documented beside it.
* [ADR-007](ADR-007.md): still the preferred, link-based recovery; [ADR-009](ADR-009.md):
  self-service email is still off by default, which is part of why a direct set
  is needed.

## Implementation Impact

* `backend/src/users/users.service.ts` - `setPasswordFor(id, password)`: refuses an
  unknown (404) or deactivated (400) account, then reuses `setPassword()` (hash +
  clear the pending reset token).
* `backend/src/users/users.controller.ts` - `@Roles('Admin') @Patch(':id/password')`
  with a `SetUserPasswordDto` (`MinLength(8)`), logging through `AdminPassword`.
* `frontend/src/api.ts` (`apiAdminSetPassword`; `AdminView.tsx`) the reset panel
  now offers **Copy link** *or* a password field + **Set password**, explaining
  that setting it invalidates the link.
* Tests - `backend/test/admin-reset-password.spec.ts` adds the direct-set path
  (new password works, old one fails, a pending link is dead, the person can still
  change it themselves) and the refusals (401/403/400 weak/400 deactivated/404,
  unknown field, and no hash in the user list).
* Docs - this ADR, a banner on ADR-007, and updates to
  [api.md](../api.md), [security.md](../security.md), the root README, the
  frontend README and the documentation index.
