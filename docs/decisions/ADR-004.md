# ADR 004: Admin-Provisioned Accounts (No Public Registration)

> **Amended (lifecycle).** Accounts have a **deactivate / reactivate** switch
> (`PATCH /users/:id/active`) beyond create/delete: deleting an account that
> ticket history references deactivates it, and its row — therefore its **email
> address** — is kept. `POST /users` with an address owned by a **deactivated**
> account therefore **revives that row** (same id, new name/role/password), so
> history keeps pointing at the same person and the address is never a dead end;
> an **active** account keeps the `409` (somebody has access — deactivate it
> first). The Users tab lists deactivated rows with a badge and the two controls
> instead of hiding them. See [api.md](../api.md) §"User management" and
> [security.md](../security.md).

## Problem Statement

The first version let anyone create an **Employee** account from the login
screen (`POST /auth/register`) and, for convenience, auto-seeded demo personas
with well-known passwords. For an internal company tool that is the wrong
default:

* an open sign-up lets anyone with network access create an account;
* shipping demo credentials into an environment is a security liability;
* the app looked like a public product rather than a controlled internal
  service where access is granted deliberately.

## Decision Options

### Option 1: Public self-registration (previous behaviour)
Convenient, but inappropriate for an internal tool and hard to audit.

### Option 2: Admin-provisioned accounts (selected) ✓
Only one account is ever seeded — the **Admin**. The Admin creates every other
account (employees and IT/HR/Maintenance agents) from inside the app, on the
**Users** tab (`POST /users`, Admin-only, explicit role and password).

### Option 3: Invite tokens / SSO
A reasonable future step, but more infrastructure than the MVP needs; documented
as out of scope.

## Selected Decision

**Accounts are Admin-provisioned; there is no public registration and no demo
seeding.**

* The backend guarantees **one** Admin, seeded from `ADMIN_EMAIL` /
  `ADMIN_PASSWORD` (default `admin@eurisko.com` / `Admin123!`). On an empty
  database that is the bootstrap; on a database that has users but **no Admin at
  all** it *recovers* the instance instead of leaving it unreachable. An existing
  Admin is never duplicated and its password is never reset, and an Admin under a
  different email is left alone.
* `POST /auth/register`, the `RegisterDto`, and the dev-only `GET /demo/accounts`
  endpoint are **removed**.
* The only account-creation path is `POST /users`, which is `@Roles('Admin')`.
* The login screen is an email + password form with no "Register" tab. Its
  password-recovery path — an Admin-issued one-time reset link
  ([ADR-007](ADR-007.md)) — is not registration and cannot create an account
  ([ADR-005](ADR-005.md)).

## Consequences & Rationale

**Benefits**
* A closed system: no outsider can create an account.
* No demo credentials exist to leak; nothing with a well-known password ships.
* Access is deliberate and auditable — the Admin decides who exists and with
  which role.
* Smaller surface: one fewer public route and no demo-discovery endpoint.

**Trade-offs**
* Onboarding is manual: someone must sign in as the Admin and create accounts.
* A brand-new environment needs the seeded Admin credentials (documented, and
  overridable with environment variables).

**Mitigation**
* The default Admin credentials are documented in the README and are the only
  seeded account; set a strong `ADMIN_PASSWORD` and `JWT_SECRET` before any real
  deployment (see [security.md](../security.md)).
* Seeding is **self-healing**: a database can never end up with no way in — as
  long as it contains no Admin, the next boot creates one from the environment.
  It only ever *adds* that account; existing users are untouched.

## Alignment with Product Requirements

* [product-spec.md](../product-spec.md) §3 — Authentication & Authorization now
  states that only the Admin is seeded and that the Admin provisions all other
  accounts; §8 Scenario 1 assumes an employee account created by the Admin.
* [architecture.md](../architecture.md) §3 — every authorization check happens
  at the API boundary; `POST /users` is guarded by `@Roles('Admin')`.

## Implementation Impact

* `backend/src/auth/` — `POST /auth/register`, `RegisterDto`, `AuthService.register`
  and the demo controller are removed; login is the only public route **that
  creates a session** (the later `reset-password` route only recovers an existing
  account — ADR-005/ADR-007).
* `backend/src/app.module.ts` — seeds only the Admin (env-overridable); no demo
  personas, no `SEED_DEMO_DATA`.
* `backend/src/common/demo-accounts.ts` — deleted.
* `frontend/src/components/AuthScreen.tsx` — login plus the reset-token mode
  (no registration).
* Test harnesses (`backend/test`, `e2e/`, `scripts/verify-slice.mjs`) provision
  their own **test fixtures** through the Admin API — they are test data, not an
  application feature.
* Docs — product spec, architecture, API reference, security notes and READMEs
  updated to match.
