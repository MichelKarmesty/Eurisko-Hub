# ADR 010: An Admin May Hard-Delete a Resolved Ticket

**Related Documents:** [Product Specification](../product-spec.md) | [Architecture Design](../architecture.md) | [Data Model](../data-model.md) | [Security Notes](../security.md) | [API Reference](../api.md) | [ADR-002](ADR-002.md) | [ADR-003](ADR-003.md)

---

## Problem Statement

ADR-003 gave the Admin a **soft** cancel: a request that should not be worked is
marked `Cancelled`, the row stays, and the history stays with it. The rule was
absolute — *tickets are never hard-deleted*, because the durable
`CREATED → CLAIMED → RESOLVED` trail is a core product requirement.

In use, that leaves the board permanently cluttered. A ticket that is genuinely
**finished and worthless** — a duplicate, a test/demo run, a mistake resolved by
accident, someone's "hello world" request — can only be cancelled, so the Admin's
list keeps growing with records nobody will ever look at again. There is no way
to say "this one is done and it does not need to exist".

The request: **let the Admin delete a ticket once it is Resolved.**

## Decision Options

### Option 1: Keep the absolute rule — not selected
Safest for auditability, but the Admin has no way to clean up finished noise, and
the tools that exist (cancel) are semantically wrong for a ticket that *was*
legitimately worked and closed.

### Option 2: Let an Admin delete a ticket in any state — not selected
The obvious extension, and the wrong one: it makes a single click (or a typo in an
id) capable of erasing work in progress and the record of a request that was never
handled. It also removes the incentive to use cancellation where cancellation is
the right answer.

### Option 3: Hard-delete only a **Resolved** ticket, Admin only — selected ✓
`DELETE /tickets/:id` removes the ticket row and its `ticket_events` in one
transaction. Only `status = 'Resolved'` qualifies:

* anything still being worked (`Open`, `In Progress`) → `409`, "cancel it instead";
* `Cancelled` → `409`, because cancellation is the audited outcome and must stay;
* unknown id → `404`; a non-Admin → `403`; no token → `401`.

Because the deletion also removes the ticket's own trace, the action is written to
the **server log** (actor, ticket id, title, category). The project still has no
separate admin-action table, so the log is the trace — the same stance ADR-007
takes for issuing reset links.

## Selected Decision

**An Admin can permanently delete a Resolved ticket; every other ticket keeps the
ADR-003 behaviour (soft cancel, record preserved).**

The UI makes the trade-off explicit before it happens: the **Delete ticket**
button (only rendered for `Resolved` rows) asks for confirmation, spelling out
that the ticket *and its entire history* leave the database and that the
requester will no longer see it — and pointing at cancel as the alternative.

## Consequences & Rationale

**Benefits**
* The Admin can keep the board meaningful: finished, worthless records can go.
* Work in progress is still protected — the destructive action is unavailable
  until the request is genuinely closed, and cancellation remains the audited way
  to retire something that should not be worked.
* No schema change, no new permission: it reuses the Admin role and the existing
  `ticket_events` cascade.

**Trade-offs**
* Deleting a resolved ticket destroys its history: the requester loses the
  record, `GET /tickets/:id/history` is gone, and the dashboard's resolved count
  drops. That is the point of the action, but it is irreversible.
* The database keeps no trace of the deletion itself; only the server log does.
* An Admin could delete a resolved ticket that someone still needed as evidence —
  mitigated by the confirmation text, not by policy.

**Mitigation**
* `Resolved` only, and `Cancelled` is explicitly refused, so the audited outcome
  cannot be silently erased.
* Explicit confirmation dialog naming the consequence; a success notice
  (`Deleted ticket #N`) afterwards.
* One log line per deletion, and the behaviour is pinned by tests
  (`backend/test/tickets.api.spec.ts`).

  override.

  status codes.

  together; nothing else references a ticket.
* [ADR-003](ADR-003.md) — kept for cancellation; its absolute "never hard-deleted"
  rule is narrowed by this decision.

## Implementation Impact

* `backend/src/tickets/tickets.service.ts` — `remove(id, user)`: Admin check, then
  `409` for `Cancelled` / anything not `Resolved`, a single transaction deleting
  the events and the ticket, and a `Tickets` log line naming the Admin.
* `backend/src/tickets/tickets.controller.ts` — `@Roles('Admin') @Delete(':id')`
  returning `{ id, mode: 'deleted' }`.
* `frontend/src/api.ts` — `apiDeleteTicket`; `AdminView.tsx` — a **Delete ticket**
  button on resolved rows plus the confirmation dialog and list removal.
* Tests — `backend/test/tickets.api.spec.ts` covers 401/403 (agent and requester),
  `409` while Open and while In Progress, `409` for a Cancelled ticket, the
  successful delete of a resolved one, and that the ticket, its history and its
  list entries are gone afterwards (404 / absent from both lists), plus `404` for
  an unknown id.
* Docs — this ADR, amendment banners on ADR-003, and updates to
  [api.md](../api.md), [security.md](../security.md), [product-spec.md](../product-spec.md),
  [architecture.md](../architecture.md), [data-model.md](../data-model.md), the root
  README and the documentation index.
