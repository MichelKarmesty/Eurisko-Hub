# ADR 005: Password Recovery, Password Change, and Any-Real-Email Accounts

## Problem Statement

ADR-004 closed the system down: only the Admin is seeded and the Admin creates
every account with a password. That left two gaps a real internal tool cannot
ship with:

* **A forgotten password had no way back.** Accounts are created by the Admin, so
  a locked-out employee had to ask the Admin to re-create the account — and the
  password was bcrypt-hashed, so nobody could *retrieve* the old one. There was
  also no way for a signed-in user to rotate their own password.
* **The app looked tied to one email domain.** The seeded Admin and every example
  used `@eurisko.com`. That is only a default, not a rule — the API already
  validated emails with `@IsEmail()` — but nothing said so, the sign-in form
  suggested `you@eurisko.com`, and the docs repeated it, so users reasonably
  assumed a company address was required.

## Decision Options

### Password recovery

1. **Store passwords reversibly so they can be "sent back"** — rejected
   outright. Reversible password storage would undo the bcrypt decision and leak
   every credential on any database read.
2. **Admin resets the password for the user** — workable, but it puts a manual
   step on the Admin for every lockout and gives the Admin a password the user
   did not choose. Kept as a fallback only (an Admin can still delete/recreate,
   and can change their own password once signed in).
3. **One-time emailed reset link + authenticated change (selected) ✓** — the
   standard, self-service path: a short-lived, single-use token by email to prove
   control of the address, and a current-password check to change it while signed
   in.

### Email delivery

1. **Add a mail-server dependency (nodemailer)** — rejected for the MVP default:
   it would add a package to a project that is otherwise zero-setup (SQLite in
   memory, offline AI fallback).
2. **Console-first with optional transports (selected) ✓** — the backend prints
   the message when nothing is configured, and an operator who wants real delivery
   sets environment variables; the first configured transport that works is used:
   a small built-in **SMTP** client (`SMTP_HOST` / `SMTP_PORT` / `SMTP_USER` /
   `SMTP_PASS` — Gmail, Outlook/Hotmail, a company server or any SMTP provider),
   an HTTP **webhook** (`MAIL_WEBHOOK_URL`), or **Resend** (`RESEND_API_KEY`).
   No new npm dependency, no code change; the SMTP client is hand-rolled on
   `node:net`/`node:tls` (`backend/src/mail/smtp.client.ts`).

### Accepted email addresses

1. **Restrict to a company domain** — rejected: the tool is generic and the
   restriction would have to be maintained; it also blocks contractors and
   personal addresses an Admin deliberately wants to add.
2. **Accept any valid address (selected) ✓** — `@IsEmail()` at every boundary;
   Gmail, Hotmail/Outlook, Yahoo and corporate domains all work identically.

## Selected Decision

**A password can be reset from a one-time emailed link or changed by its owner;
any valid email address is accepted.**

* `POST /auth/forgot-password` (public) always answers the **same generic
  message**, registered or not, so it cannot enumerate accounts. For a real,
  active account it generates `randomBytes(32)`, stores **only the SHA-256 hash**
  plus an expiry (default 30 minutes), and hands the reset link to `MailService`.
* `POST /auth/reset-password` (public) consumes the token once and replaces the
  password. Unknown, used or expired tokens get one generic `400`. The token is
  cleared on success, so a link can never be replayed.
* `POST /auth/change-password` (authenticated) requires the **current** password,
  so a stolen session token alone cannot take over the account.
* A password change through either path also invalidates any outstanding reset
  token: both fields are cleared.
* `MailService` never throws: with no provider configured it logs to the backend
  console; a provider failure falls back to the console. Recovery therefore works
  even when email does not.
* Outside production the one-time token is also returned in the HTTP response
  (`PASSWORD_RESET_RETURN_TOKEN`, **always off** when `NODE_ENV=production`) so
  the whole flow is demonstrable with no mail server — the same "works with
  nothing configured" posture as the offline AI classifier. Production deployments
  configure a provider and let the email carry the link.
* Emails are validated with `@IsEmail()` only. Personal providers and corporate
  domains are equally valid; the UI placeholder and documentation use real
  domains instead of implying `@eurisko.com`.

## Consequences & Rationale

**Benefits**
* Self-service recovery: a locked-out person no longer depends on the Admin.
* No plaintext passwords anywhere; the database only ever holds bcrypt hashes and
  a hashed, expiring reset token.
* Non-enumerating: forgot-password and login both answer identically for unknown
  accounts.
* Zero new dependencies and zero-setup development; production email is a
  configuration change, not a code change.
* The email rule is explicit and documented instead of implied by examples.

**Trade-offs**
* With no provider configured the reset link goes to the server console — correct
  for development, useless for a real user, which is why the docs say to set a
  provider before deployment.
* Returning the token in non-production responses is a deliberate development
  convenience; `NODE_ENV=production` removes it unconditionally.
* Reset links are stateless with respect to sessions: changing a password does
  not revoke already-issued JWTs. Session revocation (a token version/`passwordChangedAt`
  check) remains out of scope for the MVP.

**Mitigation**
* Documented provider variables and a production warning in
  [security.md](../security.md).
* The authenticated change path always asks for the current password.
* Tests pin the security-relevant properties: generic responses, single use,
  expiry rejection, current-password requirement, and reset-token invalidation
  (`backend/test/auth-password.spec.ts`).

  `findByResetTokenHash`, `setPassword` (hashes, clears the token).

  `ChangePasswordDto`; `LoginDto` unchanged.
* `backend/src/auth/auth.service.ts` — `forgotPassword`, `resetPassword`,
  `changePassword`; `POST /auth/login` unchanged.
* `backend/src/auth/auth.controller.ts` — the three new routes
  (`forgot-password`/`reset-password` public, `change-password` authenticated).
* `backend/src/mail/` — new `MailModule`/`MailService` plus a dependency-free

  SMTP / webhook / Resend when configured, console otherwise, never throws.
* `frontend/src/components/AuthScreen.tsx` — sign-in plus Forgot/Reset modes and
  a `?resetToken=…` deep link; `ChangePasswordDialog.tsx` — the signed-in change
  form, reachable from the top bar (`App.tsx`).

  `apiChangePassword`.

  gmail/hotmail/outlook/corporate addresses.
* Docs — READMEs, API reference, security notes, data model, architecture,
  product spec and ADR-004 updated to match.

## Amendment — ADR-007 removed the self-service path; ADR-008 restored it

The decision above delivered `POST /auth/forgot-password` plus a mail subsystem
(SMTP / webhook / Resend / console). In practice that made account recovery depend
on infrastructure (a mail provider) the rest of the product never needed, and the
"console fallback" is not a usable recovery route for the person who forgot their
password.

[ADR-007](ADR-007.md) replaced the **initiation** of recovery:

* **Removed:** `POST /auth/forgot-password`, `AuthService.forgotPassword`,
  `ForgotPasswordDto`, the whole `backend/src/mail/` subsystem (and
  `mail-smtp.spec.ts`), the mail environment variables, the
  `scripts/setup-mail.mjs` / `scripts/verify-mail.mjs` tooling, and the sign-in
  screen's "Forgot password?" link.
* **Kept:** `POST /auth/reset-password` (it now completes an Admin-issued link),
  `POST /auth/change-password`, the hashed/expiring/single-use token fields, and
  the any-real-email rule.
* **Added:** Admin-initiated `POST /users/:id/reset-password`, the **Reset
  password** action on the Users tab, and the offline `scripts/reset-password.mjs`
  break-glass for a lone Admin who has locked themselves out.

`PASSWORD_RESET_RETURN_TOKEN` went with the endpoint that used it: the Admin reset
returns the link by design, because handing it over *is* the delivery mechanism.

[ADR-008](ADR-008.md) later **reversed the removal**: self-service
`POST /auth/forgot-password` and the mail subsystem are restored (plus a
per-address anti mail-bomb cooldown), while the ADR-007 Admin path and offline
script stay as fallbacks.
