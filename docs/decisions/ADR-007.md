# ADR 007: Admin-Initiated Password Reset

## Problem Statement

Password recovery (`POST /auth/forgot-password`, ADR-005) was built around a mail
provider. Where no mail server is configured, it still "works" only through
deliberate development fallbacks: the link is printed to the backend console and
returned in the API response (`PASSWORD_RESET_RETURN_TOKEN`).

That leaves a real operational gap for this product. Eurisko Hub is an **internal
tool**: accounts are created by the Admin and there is no public registration
(ADR-004). When an employee, an agent — or an Admin — forgets their password,
there is a natural person responsible for getting them back in: the Admin. Yet
the only recovery path was one that depends on infrastructure (SMTP) the app does
not require anywhere else.

The question: should the Admin be able to start a password reset for another
account, and if so, should the Admin **set** the password or only **hand over** a
link to it?

## Decision Options

### Option 1: Do nothing — rely on the email path
Keep `forgot-password` as the only recovery. Simple, but it makes account
recovery depend on a mail server that the rest of the product does not need, and
gives the Admin (who owns the account lifecycle) no tool for the situation they
actually face.

### Option 2: The Admin types a temporary password — not selected
`PATCH /users/:id/password` sets a new password directly. Rejected: the Admin
then **knows** (and briefly *is*) the user's credential, which is exactly the
property a reset is supposed to avoid. It also needs a new
`mustChangePassword` column and a forced-change-on-next-login flow, and it leaves
the user unable to distinguish "my password" from "the password the Admin set".

### Option 3: The Admin mints a one-time link — selected ✓
`POST /users/:id/reset-password` (Admin only) creates the **same** single-use,
hashed, time-limited token the email flow uses and **returns the link** to the
Admin, who hands it to the employee. The employee sets their own password through
the unchanged `POST /auth/reset-password`. The Admin never sees or chooses it.

Reuses `UsersService.setPasswordResetToken()` / `findByResetTokenHash()` /
`setPassword()` and `AuthService.hashToken()` — **no schema change**, one code
path consumes both the emailed and the hand-delivered link, so single-use,
expiry and "a change clears any outstanding token" apply identically.

## Selected Decision

**An Admin can issue a one-time password reset link for any active account; the
Admin never sets or learns the password.** The endpoint is Admin-only
(`@Roles('Admin')`), refuses a deactivated account, logs who issued a link for
whom, and always returns the raw token because handing it over *is* the delivery
mechanism.

**Self-service `forgot-password` is removed.** Keeping it would preserve exactly
the mail-provider dependency this decision exists to drop, and an
Admin-initiated reset needs a *second* Admin — so the lone-Admin lockout it used
to cover is handled instead by an **offline break-glass**:
`scripts/reset-password.mjs` mints the same one-time token straight into the
SQLite file (run with the backend stopped). That keeps ADR-004's "a database can
never be locked out" guarantee without any external service.

**`POST /auth/reset-password` is kept.** It is what *completes* an Admin-issued
link — the employee's own new password is set there, so the Admin still never
sees or chooses it.

## Consequences & Rationale

**Benefits**
* Account recovery no longer depends on a mail server, matching the zero-setup
  posture of the rest of the project (SQLite, the offline AI classifier).
* The Admin never holds the user's credential — the security property ADR-005
  protects is preserved.
* No new table, no new column, no new token format: the existing hash + expiry +
  single-use guarantees carry over unchanged.
* Fits the existing account model: Admin already creates, re-roles and deletes
  accounts (ADR-004), so recovery belongs with them.

**Trade-offs**
* A reset link is a **credential**. Anyone who reads the Admin's screen (or the
  response) can set that account's password until the link expires. This is
  inherent to "hand it over" and is why the action is Admin-only and logged.
* An Admin can, in principle, take over any non-Admin account — no worse than the
  existing `DELETE`/role powers, but worth stating plainly.
* The raw token is always returned by this endpoint, so a deployment that treats
  "no live token in any API response" as a hard rule cannot use hand-over
  recovery at all and would have to re-introduce a mail path. The offline
  `scripts/reset-password.mjs` avoids the API response but still writes a live
  token into the database file.

**Mitigation**
* Admin-only (`403` otherwise) and authenticated (`401` otherwise); a deactivated
  account is refused (`400`).
* Single-use, expiring (`PASSWORD_RESET_TTL_MINUTES`, default 30); issuing a new
  link invalidates the previous one.
* The action is logged (`AdminReset`: which Admin, which account, when) — the log
  is the trace, as there is no user-action audit table.
* `APP_BASE_URL` is the only thing that determines where the link points, so an
  operator can keep the hand-off on a trusted origin.
* The lone-Admin lockout is covered offline by `scripts/reset-password.mjs`, which
  reuses the same token storage (hash + expiry) and warns when the API is running
  so it cannot be silently overwritten.

## Implementation Impact

* `backend/src/auth/auth.service.ts` — `issuePasswordReset(targetId)`; the
  `forgotPassword` method, `MailService` injection and `exposeResetToken` switch
  removed.
* `backend/src/auth/admin-reset.controller.ts` — `POST /users/:id/reset-password`,
  `@Roles('Admin')`, logs the action; registered in `auth.module.ts` (the auth
  module owns the token machinery; the route keeps the `/users` prefix).
* **Removed:** `backend/src/mail/` (the whole SMTP/webhook/Resend subsystem),
  `backend/test/mail-smtp.spec.ts`, `scripts/setup-mail.mjs`,
  `scripts/verify-mail.mjs`, `ForgotPasswordDto`, the `POST /auth/forgot-password`
  route, and the mail / `PASSWORD_RESET_RETURN_TOKEN` environment variables.
* **Added:** `scripts/reset-password.mjs` — the offline lone-Admin break-glass.
* `frontend/` — `AdminView.tsx` (**Reset password** on the Users tab, showing the
  one-time link with a **Copy** button), `AuthScreen.tsx` (the "Forgot password?"
  link removed; the reset form is reached from the link or an **I have a reset
  token** button), `api.ts`, `types.ts`, `styles.css`.
* Tests — `backend/test/admin-reset-password.spec.ts` (401/403/404/400, link
  issuance, use-once, re-issue invalidation, no hash leak) and a rewritten
  `backend/test/auth-password.spec.ts` (reset/change, any-email, no-leak, and a
  regression asserting `POST /auth/forgot-password` is gone).
* Docs — [api.md](../api.md), [security.md](../security.md), ADR-005's amendment,
  the root and frontend READMEs, and this ADR.
