# ADR 006: Advisory AI Request Intake

## Problem Statement

The MVP specification originally put AI out of scope (product-spec §7). In
practice, an employee who is not sure whether their problem belongs to IT, HR or
Maintenance (or how urgent it is) has to guess before they can open a ticket.
Week 4 asked for AI help at intake. Two questions had to be answered:

1. Should an AI be involved at intake at all, given the original non-goal?
2. If yes, **where does its answer go** - straight onto the ticket, or to the
   employee as a suggestion?

The second question is the dangerous one. Putting a model on the write path of
the product's source of truth would make an unpredictable component responsible
for the category and priority of every request, and would remove a decision the
product explicitly assigns to a person.

## Decision Options

### Option 1: No AI (the original non-goal)
Keep the spec as written. Simple and fully predictable, but it leaves the
classification burden entirely on the employee and gives up the one place where
a model genuinely helps without owning anything.

### Option 2: AI on the write path (auto-create / server-side pre-classify) - not selected
The model (or a server-side call to it) decides the category and priority, or
even opens the ticket. Rejected: it puts an untrusted, changing component on the
write path, removes the employee's decision (product-spec §3), and forces every
existing guarantee (DTO validation, RBAC, the `CREATED` audit event, the single
writer) to grow an exception.

### Option 3: Advisory suggestion, validated, with a labelled fallback - selected ✓
A read-only endpoint returns a **candidate** for a human to accept, edit or
ignore:

* `POST /tickets/ai-suggest` (authenticated, no side effects) answers with
  `{ suggestion: { category, priority, title, confidence }, source }` or a
  graceful error.
* `coerceSuggestion()` is the **only** constructor of a suggestion and can emit
  only members of `CATEGORIES` / `PRIORITIES`; model output is treated exactly
  like an untrusted request body.
* The AI module imports **no TypeORM feature module**, so it has no repository to
  write through - advisory-only is a property of the wiring, not a promise.
* The employee decides; the unchanged `POST /tickets` remains the only way a
  ticket is created.
* If no model answers, a small pure keyword classifier answers and is returned
  with `source: "offline"` plus a `notice`, and the UI tags it
  **"Suggested (offline)"** - rules are never passed off as the model's work.

## Selected Decision

**The AI is an advisory intake assistant only.** It suggests form fields, the
employee disposes, model output is validated against the domain enums, and the
capability degrades to a **labelled offline classifier** rather than blocking
the workflow. There is no autonomous AI: no auto-creation, no auto-assignment,
no agent-side AI, no stored prompts or answers.

## Consequences & Rationale

**Benefits**
* Keeps the authority where the product puts it: the employee chooses category
  and priority.
* No new write path - `TicketsService.create()` stays the single insert, so every
  existing guarantee keeps applying unchanged.
* Works out of the box: any OpenAI-compatible provider (the default is Groq's
  free cloud API) or a keyless local model, and with nothing configured the
  labelled offline fallback still fills the form.
* Hardened like the rest of the boundary: the validator has the final word, so a
  value like `{"category":"Finance","priority":"Urgent"}` can never leave the
  service.
* No schema change and no stored AI data - the answer is never persisted.

**Trade-offs**
* Adds an **optional** external dependency (a cloud model). It is never required:
  with no key/provider the app runs on the offline fallback.
* Adds one route and a small module to reason about, plus an eval suite.
* The offline classifier is rules, not AI; it is deliberately capped at 0.6
  confidence and labelled, so it cannot masquerade as the model.

**Mitigation**
* `AI_ENABLED=false` switches the feature off; `AI_OFFLINE_FALLBACK=false`
  restores the strict provider-only contract `{ suggestion: null, error }`.
* `AI_PROVIDER_URL` / `AI_MODEL` accept any OpenAI-compatible endpoint (a local
  Ollama needs no key), so there is no vendor lock-in.
* Every failure mode (no provider, timeout, HTTP error, non-JSON answer) is caught
  and reported - the endpoint never returns `500` and never blocks ticket creation.

## Alignment with Product Requirements

* [product-spec.md](../product-spec.md) §3 now lists **AI-Assisted Intake** as a
  functional requirement; §7 narrows the original non-goal from "No AI" to
  **"No autonomous AI"**; §8 adds Scenario 5.
* [architecture.md](../architecture.md) §2 adds the AI Intake Module; §3 states
  that AI output is untrusted input; §1 notes the model provider is an optional
  dependency.
* [data-model.md](../data-model.md) is unchanged by design: the AI stores nothing
  and no column was added.
