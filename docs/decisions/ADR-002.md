# ADR 002: Admin Override Policy

**Related Documents:** [Product Specification](../product-spec.md) | [Architecture Design](../architecture.md) | [Data Model](../data-model.md) | [ADR-001: Ticket Assignment](ADR-001.md) | [API Reference](../api.md)

---

## Problem Statement

[ADR-001](ADR-001.md) makes assignment manual: a ticket sits `Open` in its
department queue until an agent claims it. Two questions follow for the Admin
role:

1. Should an Admin be able to change a ticket's status at all? The product
   spec originally deferred this ("Admin actions beyond viewing can be added
   later").
2. If yes, what stops an Admin from closing a ticket that **no agent ever
   claimed** - silently bypassing the queue and leaving the ticket with no
   owner?

The second behaviour is the dangerous one: a ticket could be `Resolved` with
`assignedToId = null` and no explanation, which makes the manual-claiming model
look meaningless.

## Decision Options

### Option 1: Admin is view-only
Match the original MVP wording: Admins see everything but change nothing.
Simple and safe, but removes a genuinely useful escape hatch (agent unavailable,
duplicate/obsolete request, manager handling something personally).

### Option 2: Unrestricted override (status quo, not selected)
Admin may change any ticket with no extra input. Maximum flexibility, but the
bypass is silent and untraceable - the problem above.

### Option 3: Explicit override with a mandatory reason and audit event (selected) ✓
Admin may still change any ticket, but when the ticket is **not assigned to the
acting Admin** the change is treated as an override:

* a non-empty `overrideReason` is **required** (`400` otherwise);
* the change is recorded as an `ADMIN_OVERRIDE` history event carrying the
  reason (and, when resolving, the resolution note);
* the ticket stays unassigned - the system never pretends an agent handled it;
* the UI marks it (`- admin override`) and the history shows exactly who acted
  and why.

## Selected Decision

**Admins may override, but never silently.** An override without a stated reason
is rejected; every override is permanently attributable.

## Consequences & Rationale

**Benefits**
* Keeps the operational escape hatch that Option 2 provides.
* Removes the "meaningless claim" failure mode: an ownerless `Resolved` ticket
  always carries an explicit, attributed reason.
* Produces a durable audit trail (`ADMIN_OVERRIDE`) distinct from normal agent
  work (`CLAIMED`, `RESOLVED`).
* Leaves the agent path completely unchanged.

**Trade-offs**
* An Admin resolving a ticket must supply **two** things - the override reason
  and the resolution note. This is deliberate friction.
* Adds a field (`overrideReason`) to the status request contract and a new
  history action to the domain vocabulary.

**Mitigation**
* The UI explains why the field is required ("this ticket has no assigned
  agent") and the backend message names the rule.
* Agents are unaffected, so the common path stays one note + one click.

## Alignment with Product Requirements

* [product-spec.md](../product-spec.md) §8, Scenario 3 states Admin actions
  beyond viewing "can be added later". This ADR is that addition, now explicit.
* [data-model.md](../data-model.md) §2 requires a resolution note before
  `Resolved`; ADR-002 adds the *governance* note on top for Admin actions.
* [architecture.md](../architecture.md) §3 requires every authorization and
  business rule to be enforced at the API boundary - the override rule lives in
  `TicketsService.changeStatus`, not the client.

## Implementation Impact

* `backend/src/tickets/dto.ts` - `UpdateStatusDto.overrideReason?`.
* `backend/src/tickets/tickets.service.ts` - `changeStatus(..., overrideReason?)`
  requires the reason when `isAdminRole(user.role) && ticket.assignedToId !== user.id`
  and writes an `ADMIN_OVERRIDE` `TicketEvent`.
* `backend/src/tickets/ticket-event.entity.ts` - `TicketAction` gains
  `ADMIN_OVERRIDE`.
* `frontend/` - `ResolveControl` (`overrideReasonRequired`), the Admin "Start
  (override)" control, and the `- admin override` marker in `TicketTable`.
* Tests - `test/tickets.database.integration.spec.ts` and
  `test/tickets.api.spec.ts` cover the `400` (no reason) and the recorded
  override; `scripts/verify-slice.mjs` checks it live.
